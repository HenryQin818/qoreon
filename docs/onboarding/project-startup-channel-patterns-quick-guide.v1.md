# 新项目启动通道分工范式速查（V1）

适用目的：
- 新启动一个项目时，先快速判断“该参考哪种现成范式”
- 不讨论细节接入，只回答“第一批通道怎么建”

## 先看结论

后续新项目启动，优先从这 3 种范式里选，不要从零发明：

1. 平台主操作面型：参考 `task_dashboard`
2. 业务交付型：参考 `企业文化诊断`
3. 轻量专项型：参考“2 + 4”最小版

## 范式一：平台主操作面型

适用场景：
- 这个项目以后会长期作为主操作面
- 需要协调多个板块、多个执行通道
- 不只是做一个业务交付，而是要长期运营

参考项目：
- `task_dashboard`

第一批建议通道：
1. `主体-总控`
2. `主体01-架构/结构门禁`
3. `子级01-运行时/后端`
4. `子级02-前端/交互`
5. `子级03-数据/契约`
6. `子级04-测试/验收`

第二批常见支撑通道：
1. `辅助01-结构治理`
2. `辅助02-原型/需求承接`
3. `辅助03-PMO/督办`
4. `辅助04-项目运维`
5. `辅助05-Git/开源/桥接`

特点：
- 中央层稳定
- 执行层清楚
- 横向治理能力比较强
- 后期会出现候选 Agent 扩容

## 范式二：业务交付型

适用场景：
- 目标是完成一个明确业务项目
- 有交付目标、业务页面、报告、发布或运营闭环
- 需要保留未来入口，但不想一开始全都启用

参考项目：
- `企业文化诊断`

第一批建议通道：
1. `主体-总任务批次`
2. `主体01-产品/业务`
3. `主体02-技术/数据`
4. `执行01-工程环境与启动`
5. `执行02-后端/API/数据`
6. `执行03-前端/页面`
7. `执行04-测试/质量`
8. `辅助01-结构管理`
9. `辅助02-项目运维`

第二批再补：
1. 配置类通道
2. 客户沟通/物料通道
3. 业务专项通道
4. 未来预留入口

特点：
- 通道适合分层管理
- 不是所有通道都要立刻建主 Agent
- 可以保留 `待启用通道` 和 `历史壳`

## 范式三：轻量专项型

适用场景：
- 先做一个明确专项
- 团队不大，目标很聚焦
- 不想一上来建太多治理通道

参考方式：
- 用 `2 + 4` 最小版，不直接抄大项目全套

第一批建议通道：
1. `主体-总控`
2. `主体01-架构/技术门禁`
3. `子级01-运行时/后端`
4. `子级02-前端/交互`
5. `子级03-数据/契约`
6. `子级04-测试/验收`

需要时再补：
1. `辅助01-结构治理`
2. `辅助02-原型/需求承接`
3. `辅助03-项目运维`

特点：
- 最容易启动
- 最适合先跑通一轮
- 后面再按需要扩支撑通道

## 启动时怎么选

直接按这个判断：

1. 如果你要一个“长期协作中台/主操作面”：
   选 `平台主操作面型`
2. 如果你要一个“明确业务项目/交付项目”：
   选 `业务交付型`
3. 如果你要一个“先把专项做起来的小项目”：
   选 `轻量专项型`

## 启动时统一要遵守的 5 条规则

1. 第一批只建正式通道，不把未来可能会用的通道一次性建满
2. 第一批每个正式通道只需 `1` 个主负责 Agent，不先堆候选 Agent
3. 临时事项优先建任务，不优先建新通道
4. 同一职责下只是执行人不够时，优先建 Agent，不优先建通道
5. 根级 `AGENTS.md` 默认纳入抽象工程理念基线；通道级只继承引用，具体细则由项目任务和验收口径补全

## 哪些通道先不要建成 live

下面这些，默认可以先有配置/目录，不一定先建主会话：

1. `待启用通道`
2. `未来预留入口`
3. `历史兼容壳`
4. `低频配置通道`

## 最小启动建议

无论哪种范式，新项目第一天都只做这几件事：

1. 选定范式
2. 冻结第一批通道
3. 给第一批正式通道各建 `1` 个主 Agent
4. 生成通讯录（CCR）
5. 做一轮初始化培训和连通性验收

## 一句话记忆版

- 平台型：参考 `task_dashboard`
- 业务型：参考 `企业文化诊断`
- 轻量型：参考 `2 + 4` 最小版
- 通道先少后多，Agent 先主后候选，临时事项先任务后通道，工程习惯先抽象基线后项目细化
